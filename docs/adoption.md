## Activate the action

Use an ordinary `pull_request` workflow for opened, synchronize, reopened, ready_for_review, edited, labeled and unlabeled events. Use no path filter. Grant only `contents: read` and `pull-requests: read`, check out the exact PR head with full history and `persist-credentials: false`, and pass the default GitHub token. No inherited secrets or application lifecycle commands are required.

The example sets PR concurrency cancellation, a job named `Code quality ratchet` and a 20-minute timeout. The action retains artifacts for seven days. Its inputs are only `github-token` and `repository-path`; policy remains in JSON. Outputs are `outcome`, `strict-exit-code` and `report-directory`. Available summary and JSON evidence are uploaded before the saved failure verdict returns.

The action compares the PR head against the merge base of that head and the target branch, not against the target tip. A merge base does not move when unrelated changes merge into the target branch, so a scan stays valid under merge pressure, and only a new head, a retarget or a moved merge base is reported stale. The deliberate cost is that the action no longer simulates merging the current target tip into the head: a regression that appears only once newly merged target code is combined with the branch is not reported until the branch merges or rebases the target branch. Check that combination locally with an in-progress merge, which the local checker compares against its exact target parent.

Enforcement policy is read from that same merge base, so a PR cannot relax its own enforcement by editing `quality-ratchet.json` in its head tree. A policy change staged on the target branch does not retroactively apply to an open branch; instead the run compares the merge-base policy with the target-tip policy and, when they differ, reports `policy-divergence` with exit code 1 until the PR rebases or merges the target branch. It is a distinct outcome from `stale` precisely because rerunning cannot clear it. The divergence check runs before any clean, advisory or exception verdict, and a `quality-exception` label does not waive it. The enforced policy is therefore fixed at the branch point until the branch takes the target branch: a tightening never reaches an open PR silently, and never reaches it without a rebase or merge. Branch protection requiring an up-to-date branch makes the two converge sooner.

The compared target-tip policy is the one read after the scan, not the one sampled before it. Merging into the target branch moves neither the PR head nor the merge base, so a policy change that lands while a scan is running leaves every other check equal; comparing only the pre-scan tip would let that pull request merge under the superseded policy. The tip observed while scanning stays in evidence, but it does not decide the verdict.

A target tip whose own `quality-ratchet.json` does not resolve — invalid JSON, a symlinked or non-regular file, an unknown gate, a future `schemaVersion` — disables the divergence check for that run instead of blocking it. The tip tree is the only policy input no pull-request gate validates, so a configuration this tool rejects can reach the target branch; failing on it would block every open pull request, including the one that repairs the configuration, and leave a direct push to a protected branch as the only remedy. The merge base and the head tree must both still resolve, so the scan and its verdict stay fully enforced, and an unknown target policy is never reported as a difference. The run records the condition in its summary and in evidence; repair the target branch to restore divergence checking.

Hosted evidence is `schemaVersion` 2 and records both revisions and both policies: `scanned.baseSha` is the compared merge base, `scanned.baseTipSha` is the target tip observed while scanning, `scanned.policyHash` is the enforced merge-base policy, and `scanned.baseTipPolicyHash` is that tip's policy. `current.baseTipSha` is the tip read after the scan and `current.baseTipPolicyHash` the policy the divergence verdict compared; the hash is `null` with `current.baseTipPolicyUnreadable` true when that tip's configuration did not resolve. A retargeted PR is stale from `baseRef` alone, so its live `current.baseSha` and `current.baseTipSha` are `null` and no merge base is resolved against the new target. A target branch force-pushed to unrelated history under the same name is also stale: the refs arrive and no merge base exists, which rerunning against the current revision does clear. A post-scan baseline fetch that fails after one retry keeps the completed report and returns its own `error` message naming that read, which is rerunnable.
